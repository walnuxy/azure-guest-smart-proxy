# 本次连接中断的证据与验收边界

依据用户提供的《问题交接.txt》，此前部署确实启动过访客代理，并将 Codex 入口改为 `127.0.0.1:17890`。后续检查发现跟踪的 Mihomo 进程已退出、17890 无监听。Codex 继续使用该端口，足以解释连接失败和反复重连。

日志未记录明确退出原因，错误日志为空，也没有对应 Windows 崩溃事件。这些信息不能证明是软件崩溃、启动会话清理、用户退出还是其他原因。此包不得把任何一种假设写成已确认根因。

WebGPT 后来的操作是重新执行代理启动脚本，使新的 Mihomo 进程恢复监听；既有 Codex 配置再次具备转发入口。它证明了重启能够恢复当时的网络链路，不代表已经查明退出原因，也不代表长期稳定性或全部应用都已验收。

## 部署应先证明后台存活，再接入应用

1. 校验官方核心与配置，使用本包的后台持久启动机制启动。
2. 从独立命令检查 listener 的 PID、可执行文件路径和本包配置路径。再次从另一条命令检查同一 PID 与创建时间仍在，防止把短命进程或 PID 重用认成成功。
3. 检查真实 HTTPS、所选出口和退出恢复机制。短期的两次采样不等于长期运行保证。
4. 上述检查通过后再修改 Codex `.env`，保留备份；由用户重新打开目标应用。
5. 在真实消息发送期间采集应用进程与实际本地代理端口连接，并由用户确认消息生成与流式返回均完成。

`Test-GuestDeployment.ps1 -TestHttps` 只检查基础设施。先在一个 PowerShell 命令中运行 `-BeginObservation`，至少 10 秒后从另一个 PowerShell 进程运行 `-ConfirmObservation`；检查同一 supervisor/core 的 PID、实际路径和创建时间、本机端口、配置和核心哈希、heartbeat、API 与 HTTPS。基线和确认分别保存为 `state/survival-baseline.json` 与 `state/readiness.json`。核心发生恢复或身份变化时应重新采样，不能仅凭新进程存在宣称原进程持续存活。脚本不启动代理、不修改 `.env` 或系统代理，不读取 `auth.json`，并始终把模型生成标为 `NotTested`。它仅证明跨独立命令存活，不证明已跨越 Codex 整个 turn。

`Diagnose-CodexRoute.ps1` 只采集应用候选进程的路径、父进程链、监听端口和当前 TCP 连接元数据。它不收集命令行、进程环境、聊天内容、请求正文、Cookies 或 token，也不关闭应用。诊断文件包含本机用户名路径和 PID，应按本地证据保存，分享前自行审阅。

## 应用身份与路由不能靠名称推断

Codex 桌面应用及辅助进程可能名为 `ChatGPT.exe`。应依据可执行路径、父进程链和进程创建信息识别；名称相同但路径证据不足的进程必须保持未分类，不能断言是独立 ChatGPT Windows 应用。

应用连接到本包端口，只证明该时刻建立了本地连接。要区分 Azure 和本地备份，还需核对本包所选出口和目标流的连接链。应用闲置时没有连接，不能反推它在直连。读取配置文件中的 `.env` 也不能证明已运行进程采用了它。

## 成功等级应分开记录

- 代理 API 返回成功：只证明本地管理接口可响应。
- HTTPS 200 或网络测试地址成功：证明该请求的 TLS/HTTP 路径可用。
- WebSocket 握手成功：只证明相应握手可完成；并不证明模型已经生成。
- 实际模型成功：应在目标应用和真实登录会话中发送消息，看到完整流式返回，检查过程中无重连，并记录对应时刻的路由证据。不得由前三项代替。

恢复机制只能提升进程退出后的恢复能力；仍应保存退出时间、退出码、PID/创建时间和重启记录。没有退出码或事件证据时，明确写“退出原因未知”，不要追溯性编造解释。
